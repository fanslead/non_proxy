# ADR-0039：订阅源状态与节点归属由 SQLite 权威管理

- 状态：已接受
- 日期：2026-08-01

## 背景

远程订阅不仅是一次配置导入。刷新必须知道某个出口属于哪个订阅、相同节点是否为更新、
哪些节点已经从最新内容移除，以及失败后能否继续使用上一次完整结果。如果只按出口名称覆盖，
手工出口、其他订阅和默认出口都可能被误改；如果把 URL/Token 一起写入 SQLite，又会扩大
秘密暴露面。

## 决策

1. V0013 新增 `subscription_source`，只保存展示名称、系统凭据引用及版本、启用状态、刷新
   间隔、乐观 revision、内容 generation、下次刷新时间、连续失败次数、稳定错误码、最近成功
   内容哈希和节点数量。完整 URL、Token 与响应内容不进入 SQLite。
2. 订阅地址凭据使用独立 `subscription_url` 类型。URL 更新时写入新的系统凭据项，再以新的
   引用和递增 revision 更新源；数据库无法从引用反推出 URL。
3. `subscription_outbound` 以订阅内稳定 `node_key` 绑定一个出口，并用全局唯一
   `outbound_id` 防止两个订阅或手工配置共同声明同一出口。刷新不允许接管没有订阅归属的
   既有出口。
4. 每次成功刷新在一个 SQLite IMMEDIATE 事务中同时校验源 revision、内容 generation、
   出口 revision、归属和默认路由，保存全部新节点，更新仍存在的节点，把缺失节点标记为
   `present = 0` 并禁用，最后一次性推进 generation、内容哈希和刷新状态。失败记录也绑定
   同一源 revision 与 generation，因此配置改变后旧请求既不能覆盖节点，也不能污染新配置
   的失败状态。任何一步失败都不留下部分节点。
5. 缺失节点如果仍是默认出口，整次刷新明确失败并保留上一代状态；不能在后台静默切断基础
   路由。被普通策略引用的缺失节点可以保留元数据但被禁用，使数据面安全失败并让 UI 提示
   用户处理。
6. 更新节点后，存储层只返回已被替换的旧凭据引用；系统凭据库的写入与事后清理由 gateway
   编排。凭据清理失败不得回滚已经权威提交的数据库状态，但必须形成用户可见告警。
7. 首次创建和地址重配置通过 `save_and_apply_refresh` 把源配置与完整节点代数放进同一个事务；
   节点失败不能留下只指向新凭据的半成品源。已有源内容哈希未变化时，`record_unchanged` 只
   更新时间与失败状态，不递增 generation、出口 revision 或凭据版本。

## 后果

- 重启后可以从 SQLite 恢复刷新时间、失败状态和节点归属，不需要重新解析秘密 URL 才能列出
  订阅。
- 节点重命名会被视为旧节点退役和新节点出现；后续刷新编排必须生成稳定、订阅命名空间内的
  `node_key` 与 `outbound_id`，不能直接信任远端名称抢占本地标识。
- 当前迁移和仓储 API 尚未开放控制 RPC，也没有定时任务。桌面端仍不能把本批描述为可用的
  自动订阅管理。

## 验收边界

仓储测试覆盖 revision/generation 冲突、配置变更后的在途请求隔离、到期查询、原子创建与
重配置回滚、未变化刷新、缺失节点退役、旧凭据清理清单、手工出口防接管以及默认出口移除时
的全事务回滚。测试不证明真实订阅网络可用、系统凭据写入成功、后台定时刷新或桌面交互已经
完成。
