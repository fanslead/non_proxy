# ADR-0024：协调 sidecar 与主配置的可恢复双文件事务

- 状态：Accepted
- 日期：2026-08-01

## 背景

主配置候选与规则 sidecar 分别正确，并不等于两者可以安全地先后覆盖。两个路径无法依靠
普通文件系统 rename 形成跨文件原子提交；进程可能在第一份文件落盘后崩溃，客户端也可能
在 prepare 与 apply 之间更新配置。若没有双文件备份、哈希前置检查和确定的恢复方向，应用
可能留下缺少引用的 sidecar、引用不存在 sidecar 的主配置，或覆盖用户刚完成的修改。

## 决策

1. `nonproxy-adapter-transaction` 的 manifest 升级到 v3。集成变更同时持久化 sidecar 候选、
   主配置候选、两者 prepare 时的备份及各自 SHA-256；所有状态目录为 owner-only，状态文件
   为 `0600`。旧 v1/v2 单文件 manifest 继续可读。
2. 服务层必须先调用 `preview_integrated` 并完成客户端原生校验，再把两个已校验候选哈希传给
   `prepare_integrated`。准备阶段重新生成候选；任一哈希变化都在创建 manifest 前失败，避免
   把校验前后的不同内容混为同一变更。
3. apply 在写入前同时检查两个目标。每个目标只允许等于 prepare 备份或本次候选；任一目标
   是第三种内容时，两个文件都不写。应用顺序固定为 sidecar 后主配置，使第一步崩溃只留下
   未被引用的托管文件。
4. rollback 先恢复主配置，再恢复 sidecar。这样即使第二步前崩溃，主配置也不会继续引用本次
   sidecar。主配置原子替换保留替换前的文件权限位，备份字节不进入日志或 RPC。
5. 启动恢复根据目标哈希推断状态：`sidecar=候选、主配置=备份` 时恢复 sidecar；反向半状态
   时恢复主配置；两者都为候选视为已应用，两者都为备份视为已准备或已回滚。包含外部内容
   的状态不自动覆盖，保留 manifest 和备份供显式处理。
6. `verify` 对集成变更要求 sidecar 和主配置都等于各自候选才返回
   `configuration_verified=true`；真实流量路径仍未验证，`path_verified` 保持 false。
7. 本阶段只提供事务内核。`adapter-host` 尚未登记主配置路径、调用双文件 API、重载客户端或
   生成路径证据，因此桌面端不能把该能力显示为已接管。

## 结果

- 进程崩溃和幂等重放不再把两个文件当作互不相关的写操作。
- 检测到的外部修改会阻断自动应用或回滚；NonProxy 只恢复能由备份/候选哈希证明归属的内容。
- 主配置及其中可能存在的凭据会短期保存在本机私有事务目录中，以换取可恢复性；安全清理只
  能在确认两项目标均已恢复备份后执行。
- 后续宿主接入必须验证完整主配置候选，再使用公开客户端重载接口，并分别记录配置、重载和
  路径三类证据。
