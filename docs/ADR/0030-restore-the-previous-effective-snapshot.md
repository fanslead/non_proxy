# ADR-0030：只恢复服务端确认的上一有效快照

- 状态：Accepted
- 日期：2026-07-31

## 背景

产品方案承诺“恢复上一个配置”，但快照版本并不等于连续的有效配置历史：pending 和 rejected
版本会占用序号，回滚本身也会创建新版本。桌面端用 `active - 1` 猜测恢复点可能选中无效
快照；先读取再回滚期间如果另一操作发布了新配置，还可能把已经过时的目标当作“上一个”。

历史快照同时携带当时的默认路由。只恢复规则或在 UI 本地改状态都会造成控制面与数据面
分裂。回滚响应进入 `PENDING_ACK` 也只表示请求已保存，不能直接显示已经恢复。

## 决策

1. SQLite 从当前 active 之前的 `superseded` 记录中选择版本号最大的快照作为唯一恢复点；
   pending、rejected 和当前 active 都不能成为“上一个配置”。
2. `ListPoliciesResponse.previous_effective_snapshot_version` 在每个分页响应中返回同一恢复点。
   桌面端把它与活动版本、待确认版本和目录 generation 一起校验；分页期间任一值变化就
   丢弃整次读取并重试。
3. `RollbackPolicySnapshotRequest` 同时携带目标版本和
   `expected_active_snapshot_version`。服务端拒绝零值，并在 `BEGIN IMMEDIATE` 事务内先
   校验活动版本，再恢复默认路由和写入新的回滚快照。并发发布后旧确认页不能继续变更状态。
4. 桌面端执行前重新读取目录，只允许目标仍是服务端返回的上一有效快照且当前没有 pending。
   页面先展示二次确认；确认后仍只显示“等待系统组件确认”，直到 Provider ACK 使新快照
   成为 active。
5. 回滚使用历史不可变 payload 重建当前系统保护规则并恢复当时的默认路由，但不删除当前
   策略草稿。用户后续仍可检查或重新发布这些草稿。

## 结果

- 普通用户不需要输入快照版本，也不会误选 rejected/pending 版本。
- 默认路由与策略快照保持单事务一致；活动版本变化时路由和快照都不写入。
- macOS 与 Windows 共用相同页面、确认和控制契约；这不等于 Windows WFP 已完成实机验收。
- 本决策只完成“恢复上一个配置”。暂停五分钟、全部直连和全部代理需要独立的有时限运行态
  覆盖模型，不能用改写持久默认路由冒充。
