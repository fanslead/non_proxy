# ADR-0018：控制事件只作为桌面状态失效信号

## 状态

已接受。

## 背景

桌面端已经通过请求/响应 RPC 读取控制面权威状态，但此前只在页面首次进入或用户手动
操作后刷新。`gatewayd` 的 `SubscribeEvents` 同时提供进程内保留队列和实时广播；若桌面
端不消费它，其他客户端、浏览器扩展或后台确认快照后，已打开页面会持续显示旧状态。

事件流不能反过来成为 UI 的权威数据源：连接可能中断，广播消费者可能落后，服务重启
后序号也会从头开始。事件 payload 还可能只包含变化摘要，不足以重建完整页面状态。

## 决策

1. 桌面启动先读取当前页面的完整 RPC 状态，再启动一个进程级事件监视器。收到响应头
   即表示订阅已建立，不等待第一条业务事件才显示“实时”。
2. 事件只用于判定哪些页面需要重新读取；ViewModel 不直接把事件 payload 合并进页面
   状态。桌面领域对象只接收序号和事件类型，敏感或不完整 payload 不越过传输层。
3. 单次订阅内要求业务事件序号为正且严格递增。无效序号、流结束、RPC 错误、HTTP/本地
   套接字错误和服务端 `DATA_LOSS` 都进入可见的“已中断，正在重连”状态。
4. 重连采用 250 毫秒到 5 秒的指数退避。每次都从 `after_sequence = 0` 重新订阅，并在
   握手成功后重新读取 Dashboard 和当前页面。这样不依赖跨 `gatewayd` 进程连续的游标；
   重复的保留事件仅触发幂等重读。
5. 200 毫秒窗口内的事件按页面影响合并，避免快照连发造成刷新风暴。快照事件使策略类
   页面失效；决策事件使活动页失效；系统/组件事件使诊断页失效；未知事件至少刷新
   Dashboard。浏览器学习候选继续由持有标签页 capability 的扩展处理。
6. 主窗口退出时取消订阅并拒绝执行已排队的 UI 回调或刷新。事件流只属于桌面 UI
   生命周期，不影响独立运行的 `gatewayd` 和数据面。

## 当前覆盖边界

当前 `gatewayd` 实际发布快照状态和学习候选两类事件。桌面端已经识别契约中的决策、
系统状态和组件健康类型，但在对应服务端生产者接通前，不把这些页面宣称为已具备实时
推送；它们仍可通过进入页面和重连后的完整 RPC 读取获得当前状态。

## 后果

- 侧栏和 Dashboard 明确展示事件订阅的连接、实时、中断和停止状态。
- 页面展示始终来自认证控制 RPC，事件重复、缺失或服务重启不会成为错误本地事实。
- Headless 测试证明映射、重连、退避状态和 UI 失效编排；真实长时间运行、后台服务重启
  与正式包中的 UI 可见性仍需平台验收。
